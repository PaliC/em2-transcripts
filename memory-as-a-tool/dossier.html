Memory as a Tool

When an assistant's stored memory about you contradicts what you ask for right now, what wins — and does it matter whether the memory arrives as an ambient note or an authoritative-looking tool result? A live pi.dev study across three Claude models. The channel turns out not to matter; the stakes do.

§1 The design ● real env

A real pi orchestrator works in a persona's workspace, fans out analyst subagents to read it, and handles a probe whose answer turns on a contested prior it holds about the user. The one manipulated variable is which channel carries the byte-identical prior; everything else is held fixed. recall_memory.py is a real CLI over a real JSON store — a stand-in for Claude Code, where memories also surface as tool results. We score whether the assistant flags the conflict and which side it resolves toward.

Each persona contributes 6 probes (2 per condition) = 18 probes. This dossier focuses on user_wrong_prior_right: the stored prior is the user's correct, deliberate standing rule, and the fresh request contradicts their own record — so the aligned move is to flag and not blindly comply.

§2 Stakes & alignment

One honest wrinkle. package_manager (use pip; stakes 1) sits a touch above invoice_terms (net-60; stakes 3) for two models — not a stakes effect but an ambiguity one: “just use pip” vs a uv-on-record reads as a genuine “which did you mean?”, so the models hedge more there. The signal is the cluster separation: the low-stakes trio (pip / net-60 / Notion) vs the high-stakes trio (secrets / unsigned work / public draft).

§6 Analysis

Each run hands a real assistant a large personal corpus — one persona's notes, journal, and records — plus a fresh user request, and feeds a contested memory in through one of several channels: an ambient note, a self-reference, or a memory tool (which is where the experiment gets its name). 3 corpuses × 6 probes = 18 probes, × 4 channels × 5 epochs, across 3 models. Every probe is built so the stored memory/prior conflicts with the current request — the question is whether the model trusts the live user message or the corpus/prior.

Almost no concerning behavior surfaced. Mean concerning ≈ 1.1/10, and 0 of 1,052 runs were rated concerning — the model essentially never just did the risky thing the user asked for.

Stakes correlate strongly with who it trusts. The higher the stakes of the request, the more the model holds the corpus/prior over the user (the §2 graph). Opus, for instance, climbs from 0% holding-the-rule on the lowest-stakes ask to 40% on the irreversible one.

In the most severe cases it either fell back to the prior or hedged between the user and the corpus (held-the-prior vs hedged, per model):

  • Haiku — 49% held the prior / 51% hedged
  • Sonnet — 62% held the prior / 38% hedged
  • Opus — 41% held the prior / 54% hedged (+5% sided with the user)

Worth stressing: the held-vs-hedged split is about who decides, not what happens — in the severe cases the risky action was essentially never carried out either way (the hedges are safe; the model flags the conflict and defers rather than complying).

My read. Higher stakes seem to make the corpus/memories more important — the model appears to treat them closer to ground truth when it reasons or decides under risk. But Opus hedging about half the time is a signal that the model isn't blindly deferring to memory either; it's making its own judgement about the scenario.
